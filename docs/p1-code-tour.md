# P1 Rust code tour

Start with `src/ui.rs`: the egui update method renders a snapshot and sends string commands through a bounded Tokio channel. A separate thread owns a Tokio runtime and calls `call::run_controlled`. The UI does not perform camera or codec work in its drawing callback. `JoinHandle` and the ended flag let it return to an editable, joinable state.

`src/controls.rs` shares a small `CallView` with `Arc`. Mutexes protect state and the latest frames; atomics handle simple flags. Cloning an `Arc<Frame>` avoids copying the RGB buffer merely to share a snapshot. The UI uploads pixels into textures when the frame timestamp changes.

`src/video.rs` owns the media stages. A `watch` channel retains the latest capture frame rather than allowing a growing backlog. Bounded `mpsc` channels correlate codec output with timestamps. `Processes` owns child processes and a `JoinSet`, making teardown explicit. FFmpeg handles camera/VP8 details; Rust checks dimensions, frame sizes, packet sequences, and queue boundaries.

`Reassembler` collects fragments for one RTP timestamp. It rejects missing/out-of-order fragments and waits for a keyframe after damage. This is a local baseline, not a complete packet-loss recovery strategy. Unit tests exercise normal fragmentation, a missing packet, and tiny final fragments.

`src/call.rs` registers and routes audio/video tracks on one WebRTC connection. Audio sending and receiving each run on a dedicated thread with their own Tokio runtime. This separates the 20/40/60 ms media tick from signaling, statistics, and CPU-heavy video workers. The session owns an `AudioWorker` guard: dropping it signals cancellation and joins the thread. An atomic mute flag lets controls change its behavior without moving device streams between threads. A completion channel reports worker failures to the session. Signaling polling remains an in-flight future in the select loop, allowing incoming tracks and controls to be handled while a response is pending. Video commands update shared state; sender cancellation stops capture/encoding. `src/audio.rs` waits for the shared-clock presentation deadline at startup/rebuffer, then lets the audio device pace contiguous PCM. It does not insert silence between samples merely because a sender tick ran a little late. The sender catches up brief scheduler stalls; stalls longer than 100 ms reset the timer instead of creating an unbounded burst. A/V playback has a bounded 240 ms capacity to accommodate a 120 ms target plus callback batching; audio-only playback has a 200 ms capacity. Startup/rebuffer reserve accounts for the incoming packet duration. Capacity is a maximum, not a deliberate delay.

`src/metrics.rs` uses atomic counters and logarithmic histograms so transport/device tasks can record observations cheaply. Percentiles are bucket upper bounds. Learn to distinguish what a metric observes (decode completion) from what a user experiences (speaker sound and displayed frames).

Try changing one video preset, running `scripts/check_p1.py`, and comparing payload bitrate, transport bitrate, and CPU. Then explain the result before making another change. Keep harsh-network experiments for P2 so each comparison has a stable baseline.
